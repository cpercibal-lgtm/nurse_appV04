# Changelog

All notable changes to the AIGH Nursing Workforce Management System. Versions follow [Semantic Versioning](https://semver.org/); while the version is `0.y.z` the system is in development and runs demonstration data only.

- **Credential types by nationality** (owner decision, 2026-10-04). A credential type now says who it applies to — every nationality, only listed nationalities, or every nationality except listed ones (Credentials → Catalog → *Applies to*, a catalog change approved by a second administrator like any other). For a nurse a type does not apply to, its requirements count as optional: the credential can still be submitted and verified but never makes the nurse ineligible; My Credentials marks it "Optional for you", and HR's Record credential list shows "Only: …" / "Optional for: …". A nurse without a listed nationality counts as none of the listed ones (so Passport stays required for them). The migration sets **Passport** and **Resident ID (Iqama)** to every nationality except Saudi, and adds **National ID** for Saudi nationals only — National ID Number (encrypted and searchable like the Iqama number: new protected category `NATIONAL_ID`, with its processing-register entry for the DPO to review), Issue Date, Expiry Date (Gregorian/Hijri), card upload required, grace 0 days until HR sets it. Which units and positions require each type is still set under Requirements. Changing a nurse's nationality, or a type's setting, re-evaluates the nurses concerned at once. The hospital baseline file carries the same settings. API: `nationalityRule` / `nationalityCodes` on `POST`/`PATCH /credential-templates` (422 `NATIONALITY_RULE_INVALID`, `NATIONALITY_INVALID`); `optionalByNationality` on `GET /credentials/me/requirements`.

### Changed
- **E-mail hourly limit** (D-69, before announcements). New setting `EMAIL_HOURLY_LIMIT` (default `0` = no limit): the e-mail dispatcher sends only what keeps the last 60 minutes under it; the rest stays Pending without using a retry attempt and goes out as the hour moves on. UltaMail allows 200 e-mails per hour per domain, so the live server should use `150`. Each run now sends outbox mail (the break-glass alert) first, then notifications most urgent first.
- **Arabic names for credential types and their fields** (owner, 2026-10-05). The Arabic interface showed every credential type and field in English ("National ID", "National ID Number"). Each type now has an Arabic name and each field an Arabic label — the 17 hospital types and their 71 fields are filled in (migration `20261024100000_credential_arabic_names`, and the hospital baseline file) — shown wherever a type or field appears when the interface is Arabic (Records, Review queue, Requirements, Catalog, My Credentials, Eligibility waivers, the credential forms, and the Arabic text of expiry, grace and SCFHS notifications); the English text when none is stored. Credentials → Catalog edits them like the English ones (four-eyes). The Arabic wording for credentials now uses الشهادة throughout (الاعتماد means approval elsewhere), and the nationality texts read more naturally. The privacy texts (My data, erasure) now name the National ID number among the numbers made unreadable on erasure, as erasure already did. API: `nameAr` on `POST`/`PATCH /credential-templates` (`null` clears it), `labelAr` in `fieldDefs`; `template.nameAr` in credential, requirement and waiver lists; the baseline format accepts both.
- On a phone, the header title stays on one line (shortened with "…"): the Arabic name wrapped under the header and ran into the page title. The menu button is labelled in the interface language.
- **Credential type settings from the hospital's credential requirements matrix** (owner, 2026-10-04). Grace days after expiry while a renewal is in progress: Passport 90; Resident ID (Iqama) and Hospital ID 30; Employment Contract and Staff Clearance 0; Professional License, SCFHS licence, Malpractice Insurance, the three competencies and the six life-support certificates 60; National ID 30 (owner, 2026-10-05; migration `20261024090000_national_id_grace`). SCFHS checks: the **Saudi Council License (SCFHS)** is checked with SCFHS and suspended at once when SCFHS reports it suspended or revoked; the matrix also asked for checks on the other types, but only a type that records an SCFHS registration number can be checked, so they stay off. The migration `20261023090000_credential_type_settings` updates existing installations (the daily 00:05 run re-evaluates every nurse); the hospital baseline file carries the same settings, and its format accepts `scfhsEnabled` / `scfhsAutoSuspend` (rejected without an SCFHS number field, or auto-suspend without checks). The Guidelines, the manual and `docs/CLINICAL_ELIGIBILITY.md` say so.
- The Arabic interface text now loads only when Arabic is used: the translations are split into `lib/i18n.en.ts` (in the main bundle) and `lib/i18n.ar.ts` (a separate 17 KB chunk), and the app renders once the chosen language is loaded, so Arabic users never see English first. The initial download fell from 196.19 KB to 179.23 KB gzipped (budget 200 KB). If Arabic cannot be loaded (offline), the app opens in English.
- **A contract renewal needs valid credentials** (owner decision, 2026-10-02). For a nurse who has had a contract before — a renewal, or a new contract after the old one ended — the contract is neither created nor approved while a required (MANDATORY) credential of their unit and position is missing, expired, not verified, suspended or revoked, or while they have no unit. The refusal (`CREDENTIALS_BLOCK_RENEWAL`) lists the credentials. Only credential reasons count — the ended contract does not, so it can always be renewed once the credentials are in order; grace, waivers and transition periods pass; a first contract is not checked (`backend/src/modules/contracts/service.ts`). The Guidelines, `docs/USER_MANUAL.md`, the PDF manual and the contract flow image say so.
- GitHub Actions moved to the releases that run on Node 24 (GitHub retires Node 20 for actions): `actions/checkout`, `setup-node`, `setup-java` and `cache` v5, `docker/setup-buildx-action` v4, `google-github-actions/auth` and `setup-gcloud` v3. Inputs and steps are unchanged.
- The backend tests include the tester walkthrough end to end (`backend/test/walkthrough.test.ts`): on a fresh database with the hospital baseline, a Saudi and a Filipino nurse go through onboarding, credentials by nationality, a New contract without a type field, the renewal rule, the two-person approval with elevation, supervisor scope and the audit chain. It runs in CI with the rest of the suite.

### Fixed
- VPS: every release left its unpacked bundle (about 1 GB) in `/var/tmp/nurseapp-release.*`, because `nurseapp-release` hands over to `deploy.sh` with `exec` and its clean-up never ran; 33 releases had used 36 GB of the 72 GB disk. It now deletes the folder before handing over (and the bundle file as soon as it is unpacked), and the VPS test fails if a work folder is left behind. Folders left by earlier releases are deleted by hand once (`ops/vps/README.md`).
- Announcements: the hint for a System Admin who has not elevated named the wrong place. It now says **Nursing Administration → Privileged access**, and the approval messages name **Nursing Administration → Approvals** (English and Arabic).
- After one refusal, New contract / Renew, Onboard employee, New account and Grant role refused every further submit in the same window with "This Idempotency-Key was already used for a different request" (another employee, other dates), and a resubmit of the same request replayed the old refusal for 24 hours even after the problem was fixed. The form now takes a new key after any answer from the server and keeps it only when the outcome is unknown (no connection, server error, still processing), so a double click or a retry is still applied once (`frontend/src/lib/idempotency.ts`).
- VPS monitoring sent a false "FAILING: containers" e-mail (then "RECOVERED") on every deploy: while colours switch, the old colour's containers stop before `ACTIVE` names the new one. `deploy.sh release` and `rollback` now leave a marker (`/srv/nurseapp/DEPLOYING`, removed on every exit); the containers check skips while it is younger than 30 minutes. The site check still reports a real outage during a deploy.
- VPS: every release left its three images behind (about 1 GB each time). After two days of releases the server held 38 images, 25 GB of them unused, so the disk would eventually fill. `deploy.sh release` now keeps the live and the previous release (a rollback needs it) and removes the older `nurseapp/*` images. A restart, or a deploy of the release that is already live, keeps the earlier release as the rollback target (before, it recorded the live release itself as "previous", and the cleanup then removed the real previous release); `deploy.sh rollback` always starts the colour that is not live, and refuses when there is no earlier release.
- `verify-install.sh` reported the firewall as FAILED ("unexpected open port: 172.17.0.1") on a correct installation: it read the address in the containers' PostgreSQL rule (`172.17.0.1 5432/tcp`) as a port. The check now reads the port of such rules; a really unexpected port, or PostgreSQL open to more than the containers, still fails.
- A restore of a VPS backup could not start: Ubuntu keeps `postgresql.conf`, `pg_hba.conf` and `pg_ident.conf` in `/etc/postgresql/15/main`, outside the data directory, so the base backup does not contain them (found by the first restore drill). `ops/backup/scripts/restore-database.sh` now writes minimal ones when they are missing — local-socket, peer authentication only.
- VPS backups could not start: every release left `/opt/nurseapp` readable by root only (`nurseapp-release` runs with `umask 077`), so PostgreSQL's `archive_command` and the nightly backup — both run as `postgres` — could not read `ops/backup/scripts`. `nurseapp-release`, `deploy.sh load` (which travels with every release, so a server with the older `nurseapp-release` is fixed too) and `setup-backup.sh` now make the released scripts readable (`u=rwX,go=rX`; they are repository files, no secrets). `ops/vps/test/run.sh` fails if a release leaves them root-only.
- The links in the invitation, password-reset and sign-in e-mail change e-mails were plain text (not clickable, and broken up beside the Arabic text). They are now a real button with the address underneath, once, between the English and Arabic text (`backend/src/lib/email-templates.ts`; the three messages pass the address as `link`). Tests fail if a link turns back into plain text.
- `ops/vps/db-init.sh` with a `DB_NAME` other than `nurseapp_v04` now also lets the containers reach that database in `pg_hba.conf`. Before, the first release stopped at its migrations ("no pg_hba.conf entry").
- `ops/vps/setup-host.sh` comments out provider lines above the `Include` in `/etc/ssh/sshd_config` that silently kept root and password sign-in on (found on UltaHost), and now stops unless `sshd -T` reports keys only and no root sign-in. On a host without an IPv6 route, `apt` uses IPv4 only (a mirror's IPv6 address had timed out mid-install).
- Production start-up now also refuses a database login that may `TRUNCATE` any table (`backend/src/lib/db-role.ts`). Before, only `ops/db/verify.sql` caught that grant; the API and worker would still have started.

### Security
- Security review (2026-10-04) of every API route, query, secret and page; findings and fixes in [docs/SECURITY_REVIEW_2026-10-04.md](docs/SECURITY_REVIEW_2026-10-04.md).
- An upload whose `X-File-Name` is not validly percent-encoded is refused with 400 `FILE_NAME_INVALID` (before: a 500 server error). Stored file names also drop invisible and direction-changing characters (such as the right-to-left override that can make `…fdp.exe` display as `…exe.pdf`) besides control characters and slashes (`backend/src/lib/uploads.ts`).
- FHIR `GET /fhir/Practitioner?identifier=` longer than 300 characters is refused with 400 `invalid`.
- The web server sends `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`: the app uses none of them, so no script can ask for them (`frontend/nginx/default.conf.template`).
- Dependencies: patch updates of dotenv 18.0.5, nodemailer 10.0.14, pg 8.23.1, @tanstack/react-query 5.104.1, vite 8.3.2, vitest 5.0.3, supertest 7.3.1 and smtp-server 3.19.17. `npm audit` reported 4 high advisories, all inside the Prisma command-line tool (`mysql2`, which only MySQL uses, and `deepmerge-ts`, which merges the project's own `prisma.config.ts`), neither reachable from a request; root `overrides` pin the fixed `mysql2` 3.24.5 and `deepmerge-ts` 8.0.2 (no fixed Prisma 7 release exists) — `npm audit` now reports 0. (`npm ls` still prints "invalid" for these two: an npm display bug with overrides in workspaces; `npm ci` installs them correctly.)

## [0.1.0] - Architecture Baseline Reset (2026-09-27)

### Added
- Consolidated monorepo baseline (Express 5, Prisma 7, React 19, PostgreSQL 15).
- Unified `/api/v1` API, single-schema Prisma migration chain, and role-based access control.
- Pure eligibility evaluation engine, database-level audit chaining, and background jobs.
- The version at the foot of the sidebar and in the FHIR `CapabilityStatement`, both read from `package.json`.

### Changed
- Reset application versioning to 0.1.0 (SemVer development baseline). The packages were numbered `4.0.0` ("V04"); no code, schema or migration changed with the number.
- `.env.example` lists every setting the backend reads (added `TELEGRAM_UPDATES`, `TELEGRAM_WEBHOOK_SECRET`, `SCFHS_DRIVER`, `SCFHS_API_URL`, `SCFHS_API_KEY`, `BADGE_SIMULATOR`).

### Superseded
- V03 (`nurse_appV03`) and its database `nurseapp` are superseded by this system. They were never part of this repository, so nothing was removed from it; what V04 dropped from V03 while being rebuilt is recorded in [docs/CLEANUP_REPORT.md](docs/CLEANUP_REPORT.md).
