# Changelog

All notable changes to the AIGH Nursing Workforce Management System. Versions follow [Semantic Versioning](https://semver.org/); while the version is `0.y.z` the system is in development and runs demonstration data only.

## [Unreleased]

### Added
- **Guidelines** (side menu, every signed-in user): the user manual inside the application — what each screen is for, every task in one template (purpose, who, before you start, steps, system result, approval, next step, common problems, related), 25 workflows drawn as images, the complete hospital workflow, troubleshooting and a quick reference; search; "Only tasks for my roles"; light, dark, Arabic interface (the guide's text is English). Every task is labelled Implemented, Partially implemented or Planned and is traced to the code in [docs/GUIDELINES_COVERAGE.md](docs/GUIDELINES_COVERAGE.md). A "?" beside the title of twelve pages opens the matching section.
- The same content as [docs/USER_MANUAL.md](docs/USER_MANUAL.md), workflow images in `docs/generated/flows/`, and a printable PDF (`docs/generated/AIGH_Nursing_Workforce_User_Manual_V04.pdf`, also downloadable from the Guidelines page), built by `npm run docs:manual` (dev dependency `pdfkit`).
- VPS: `REDIRECT_HOSTS` in `/etc/nurseapp/deploy.env` (space-separated, in double quotes: bash reads the file) — names such as the bare domain and `www` that permanently redirect to `https://SITE_HOST`, each with its own certificate (`ops/vps/Caddyfile`, `deploy.sh edge`). Empty by default: nothing changes.
- VPS: `monitor.sh --test-alert` sends one test alert to the recipients in `/etc/nurseapp/monitor.env` without running the checks, and exits 1 with the reason if nothing could be sent (`ops/vps/README.md`). The VPS test checks it against its test mail server.
- **Credentials → Records → Record credential for a nurse** (HR Admin, System Admin): HR records a licence or certificate on a nurse's behalf — search the nurse in scope, choose the type, fill in its fields; the Evidence panel then opens for the upload. Uses the existing `POST /credentials` (scoped, audited, starts Pending verification). Before, only the nurse could add a credential on screen. The Guidelines, the manual and the coverage matrix say so.

- **Employment Contract Type** on contracts (owner decision, 2026-10-03). Onboard employee requires a type from a hospital-wide list. New contract and renewal do not ask for it (owner decision, 2026-10-04): they carry the employee's previous contract's type while it is still active, otherwise "Not classified"; the API still accepts `contractTypeCode`. The contract list shows it (in English or Arabic) and can be filtered by it. **Contracts → Contract types**: system-wide HR and System Admins add, edit and delete types — a type no contract uses is deleted, a used one is deactivated (hidden from new contracts, kept on old ones); every change audited. The migration creates the list with Direct Hospital Employment, MOH / Government Contract, Private Sector Contract, Outsourcing / Manpower Contract, Agency Contract, Temporary Contract and SOP, with Arabic names; existing contracts stay "Not classified". Information only — eligibility, renewal and approval rules do not read it. API: `contractTypeCode` required on `/employees/onboard`, optional on `POST /contracts` and `/contracts/:id/renew`; `GET`/`POST`/`PATCH`/`DELETE /contract-types`.

- **Nationality from a standard list** (owner decision, 2026-10-03). Onboard employee and Edit now offer a searchable dropdown — type the nationality, the country or the code — instead of free text, and nationality is required. The list is fixed (it changes only with a release): ISO 3166-1 alpha-3 codes as on passports, 200 entries — the 193 UN member states, the Holy See, Palestine, Kosovo (XKX), Taiwan, Hong Kong, Macau and Stateless (ICAO XXA) — with English and Arabic names, alphabetical. Employees store the code (`nationality_code`); the server refuses free text and unlisted codes (`NATIONALITY_INVALID`). The migration maps nationalities already typed in (the nationality, the country, the code or the Arabic name in any case and spacing, and a few unambiguous spellings such as UAE or Filipina) to codes; anything it cannot match is kept as typed and shown as "not on the nationality list" until HR chooses one on Edit — nothing is deleted. The dropdown (`components/NationalitySelect.tsx`) can be reused wherever a nationality is chosen. API: `GET /nationalities`; `nationalityCode` on `POST /employees/onboard` and `PATCH /employees/:id`.

- **Rank/Grade master** (owner decision, 2026-10-03). Rank/Grade is now the SCFHS nursing classification, required, and chosen in a **Select Rank/Grade** window (search by code, classification or meaning; click and Select, or double-click) on Onboard employee and Edit — the SCFHS licence's Professional Classification uses the same window and list. **Workforce → Rank/Grade**: hospital-wide HR and System Admins add, edit, deactivate, reactivate and delete records (search; filter All/Active/Inactive); the code never changes; a record used by employees or licences cannot be deleted — the screen offers to deactivate it; every change is audited with old and new values. Starting list: N01 Senior Specialist Consultant Nurse, N02 Senior Specialist Nurse, N03 Specialist Nurse, N04 Technician Nurse, N05 Health Assistant Nurse. Employees store the code (`rank_grade_code`); the server refuses free text, unlisted codes and new choices of an inactive record. The migration maps existing text that is a listed code or classification; anything else (pay grades such as "Grade 7") is kept as typed and shown as "not on the Rank/Grade list" until HR chooses one. API: `GET`/`POST`/`PATCH`/`DELETE /rank-grades`; `rankGradeCode` on `POST /employees/onboard` and `PATCH /employees/:id`.

- **Nursing Specialty master** (owner decision, 2026-10-03). Specialty is now required on Onboard employee and Edit, chosen from a searchable dropdown ("Select Nursing Specialty"; search by code, name or description) in the master's sort order. **Workforce → Specialty**: hospital-wide HR and System Admins add, edit, deactivate, reactivate and delete specialties (search; filter All/Active/Inactive); the code never changes; names are unique ignoring case; delete asks for confirmation and, for a specialty employees hold, offers to deactivate instead; every change is audited with old and new values. Starting list: 34 specialties, NS001 Clinical Nursing … NS034 General / Unspecified, with Arabic names. Employees store the code (`specialty_code`); supervisors still see the specialty. The migration maps text that is a listed name, Arabic name or code, or a clear short form (ICU, NICU, Critical Care, Emergency, ER, Neonatal, Medical-Surgical, Obstetrics, Midwifery and similar); ambiguous text ("Surgical", "Management", "General") and anything else is kept as typed and shown as "not on the specialty list" until HR chooses one. API: `GET`/`POST`/`PATCH`/`DELETE /nursing-specialties`; `specialtyCode` on `POST /employees/onboard` and `PATCH /employees/:id`.

- **Job Post (City) as Region + City** (owner decision, 2026-10-03). Onboard employee and Edit open a **Select Job Post Location** window: choose the Region / Province, then a city of that region only (the city list stays disabled until a region is chosen and is cleared when the region changes); both searchable; Select is enabled once both are chosen. The field shows "Qassim Region - Buraydah" (Arabic in Arabic) and is required; supervisors still do not see it. **Workforce → Locations**: hospital-wide HR and System Admins add, edit, deactivate, reactivate and delete regions and cities; region codes are ISO 3166-2 (SA-01 …) and never change; a region with cities or employees, or a city employees hold, cannot be deleted (the screen offers to deactivate it) and a held city cannot move to another region; every change is audited. Starting list: the 13 regions and 108 cities given by the owner, with Arabic names ("Al Badai" for البدائع). Employees store the region code and the city id; the server checks the city belongs to the region and refuses free text. The migration maps text that is exactly a listed city (English or Arabic) or "Region - City"; anything else (e.g. "Riyadh - Al Iman Hospital") is kept as typed and shown as "not on the location list". API: `GET`/`POST`/`PATCH`/`DELETE /saudi-regions`, `/saudi-cities`; `jobPostRegionCode` + `jobPostCityId` on `POST /employees/onboard` and `PATCH /employees/:id`.

- **Actual Work Place / Facility from a Facility master** (owner decision, 2026-10-03). Onboard employee and Edit offer a searchable "Select Facility" dropdown, required; supervisors still see it. **Manage Facilities** beside the field (hospital-wide HR and System Admins only) and **Workforce → Facilities** add, edit, deactivate, reactivate and delete facilities: names trimmed with single spaces and unique ignoring case; a facility added from the form is selected at once and the form keeps what was typed; edit keeps the facility's id so every employee shows the new name; delete confirms with the name, and a facility employees use cannot be deleted — the screen offers to deactivate it; a choice not yet saved that is deleted or deactivated is cleared with a message; every change is audited. Starting list: the 10 hospitals given by the owner, with Arabic names. Employees store `facility_id`. The migration maps text that is exactly a listed facility (English or Arabic, any capitals or spacing); anything else — the demo's wards such as "ICU Main" — is kept as typed and shown as "not on the facility list". API: `GET`/`POST`/`PATCH`/`DELETE /facilities`; `facilityId` on `POST /employees/onboard` and `PATCH /employees/:id`.

- **Credential types by nationality** (owner decision, 2026-10-04). A credential type now says who it applies to — every nationality, only listed nationalities, or every nationality except listed ones (Credentials → Catalog → *Applies to*, a catalog change approved by a second administrator like any other). For a nurse a type does not apply to, its requirements count as optional: the credential can still be submitted and verified but never makes the nurse ineligible; My Credentials marks it "Optional for you", and HR's Record credential list shows "Only: …" / "Optional for: …". A nurse without a listed nationality counts as none of the listed ones (so Passport stays required for them). The migration sets **Passport** and **Resident ID (Iqama)** to every nationality except Saudi, and adds **National ID** for Saudi nationals only — National ID Number (encrypted and searchable like the Iqama number: new protected category `NATIONAL_ID`, with its processing-register entry for the DPO to review), Issue Date, Expiry Date (Gregorian/Hijri), card upload required, grace 0 days until HR sets it. Which units and positions require each type is still set under Requirements. Changing a nurse's nationality, or a type's setting, re-evaluates the nurses concerned at once. The hospital baseline file carries the same settings. API: `nationalityRule` / `nationalityCodes` on `POST`/`PATCH /credential-templates` (422 `NATIONALITY_RULE_INVALID`, `NATIONALITY_INVALID`); `optionalByNationality` on `GET /credentials/me/requirements`.

### Changed
- **Credential type settings from the hospital's credential requirements matrix** (owner, 2026-10-04). Grace days after expiry while a renewal is in progress: Passport 90; Resident ID (Iqama) and Hospital ID 30; Employment Contract and Staff Clearance 0; Professional License, SCFHS licence, Malpractice Insurance, the three competencies and the six life-support certificates 60; National ID stays 0 until HR sets it. SCFHS checks: the **Saudi Council License (SCFHS)** is checked with SCFHS and suspended at once when SCFHS reports it suspended or revoked; the matrix also asked for checks on the other types, but only a type that records an SCFHS registration number can be checked, so they stay off. The migration `20261023090000_credential_type_settings` updates existing installations (the daily 00:05 run re-evaluates every nurse); the hospital baseline file carries the same settings, and its format accepts `scfhsEnabled` / `scfhsAutoSuspend` (rejected without an SCFHS number field, or auto-suspend without checks). The Guidelines, the manual and `docs/CLINICAL_ELIGIBILITY.md` say so.
- The Arabic interface text now loads only when Arabic is used: the translations are split into `lib/i18n.en.ts` (in the main bundle) and `lib/i18n.ar.ts` (a separate 17 KB chunk), and the app renders once the chosen language is loaded, so Arabic users never see English first. The initial download fell from 196.19 KB to 179.23 KB gzipped (budget 200 KB). If Arabic cannot be loaded (offline), the app opens in English.
- **A contract renewal needs valid credentials** (owner decision, 2026-10-02). For a nurse who has had a contract before — a renewal, or a new contract after the old one ended — the contract is neither created nor approved while a required (MANDATORY) credential of their unit and position is missing, expired, not verified, suspended or revoked, or while they have no unit. The refusal (`CREDENTIALS_BLOCK_RENEWAL`) lists the credentials. Only credential reasons count — the ended contract does not, so it can always be renewed once the credentials are in order; grace, waivers and transition periods pass; a first contract is not checked (`backend/src/modules/contracts/service.ts`). The Guidelines, `docs/USER_MANUAL.md`, the PDF manual and the contract flow image say so.
- GitHub Actions moved to the releases that run on Node 24 (GitHub retires Node 20 for actions): `actions/checkout`, `setup-node`, `setup-java` and `cache` v5, `docker/setup-buildx-action` v4, `google-github-actions/auth` and `setup-gcloud` v3. Inputs and steps are unchanged.
- The backend tests include the tester walkthrough end to end (`backend/test/walkthrough.test.ts`): on a fresh database with the hospital baseline, a Saudi and a Filipino nurse go through onboarding, credentials by nationality, a New contract without a type field, the renewal rule, the two-person approval with elevation, supervisor scope and the audit chain. It runs in CI with the rest of the suite.

### Fixed
- After one refusal, New contract / Renew, Onboard employee, New account and Grant role refused every further submit in the same window with "This Idempotency-Key was already used for a different request" (another employee, other dates), and a resubmit of the same request replayed the old refusal for 24 hours even after the problem was fixed. The form now takes a new key after any answer from the server and keeps it only when the outcome is unknown (no connection, server error, still processing), so a double click or a retry is still applied once (`frontend/src/lib/idempotency.ts`).
- VPS monitoring sent a false "FAILING: containers" e-mail (then "RECOVERED") on every deploy: while colours switch, the old colour's containers stop before `ACTIVE` names the new one. `deploy.sh release` and `rollback` now leave a marker (`/srv/nurseapp/DEPLOYING`, removed on every exit); the containers check skips while it is younger than 30 minutes. The site check still reports a real outage during a deploy.
- VPS: every release left its three images behind (about 1 GB each time). After two days of releases the server held 38 images, 25 GB of them unused, so the disk would eventually fill. `deploy.sh release` now keeps the live and the previous release (a rollback needs it) and removes the older `nurseapp/*` images. A restart, or a deploy of the release that is already live, keeps the earlier release as the rollback target (before, it recorded the live release itself as "previous", and the cleanup then removed the real previous release); `deploy.sh rollback` always starts the colour that is not live, and refuses when there is no earlier release.
- `verify-install.sh` reported the firewall as FAILED ("unexpected open port: 172.17.0.1") on a correct installation: it read the address in the containers' PostgreSQL rule (`172.17.0.1 5432/tcp`) as a port. The check now reads the port of such rules; a really unexpected port, or PostgreSQL open to more than the containers, still fails.
- A restore of a VPS backup could not start: Ubuntu keeps `postgresql.conf`, `pg_hba.conf` and `pg_ident.conf` in `/etc/postgresql/15/main`, outside the data directory, so the base backup does not contain them (found by the first restore drill). `ops/backup/scripts/restore-database.sh` now writes minimal ones when they are missing — local-socket, peer authentication only.
- VPS backups could not start: every release left `/opt/nurseapp` readable by root only (`nurseapp-release` runs with `umask 077`), so PostgreSQL's `archive_command` and the nightly backup — both run as `postgres` — could not read `ops/backup/scripts`. `nurseapp-release`, `deploy.sh load` (which travels with every release, so a server with the older `nurseapp-release` is fixed too) and `setup-backup.sh` now make the released scripts readable (`u=rwX,go=rX`; they are repository files, no secrets). `ops/vps/test/run.sh` fails if a release leaves them root-only.
- The links in the invitation, password-reset and sign-in e-mail change e-mails were plain text (not clickable, and broken up beside the Arabic text). They are now a real button with the address underneath, once, between the English and Arabic text (`backend/src/lib/email-templates.ts`; the three messages pass the address as `link`). Tests fail if a link turns back into plain text.
- `ops/vps/db-init.sh` with a `DB_NAME` other than `nurseapp_v04` now also lets the containers reach that database in `pg_hba.conf`. Before, the first release stopped at its migrations ("no pg_hba.conf entry").
- `ops/vps/setup-host.sh` comments out provider lines above the `Include` in `/etc/ssh/sshd_config` that silently kept root and password sign-in on (found on UltaHost), and now stops unless `sshd -T` reports keys only and no root sign-in. On a host without an IPv6 route, `apt` uses IPv4 only (a mirror's IPv6 address had timed out mid-install).
- Production start-up now also refuses a database login that may `TRUNCATE` any table (`backend/src/lib/db-role.ts`). Before, only `ops/db/verify.sql` caught that grant; the API and worker would still have started.

### Security
- Security review (2026-10-04) of every API route, query, secret and page; findings and fixes in [docs/SECURITY_REVIEW_2026-10-04.md](docs/SECURITY_REVIEW_2026-10-04.md).
- An upload whose `X-File-Name` is not validly percent-encoded is refused with 400 `FILE_NAME_INVALID` (before: a 500 server error). Stored file names also drop invisible and direction-changing characters (such as the right-to-left override that can make `…fdp.exe` display as `…exe.pdf`) besides control characters and slashes (`backend/src/lib/uploads.ts`).
- FHIR `GET /fhir/Practitioner?identifier=` longer than 300 characters is refused with 400 `invalid`.
- The web server sends `Permissions-Policy: camera=(), microphone=(), geolocation=(), payment=(), usb=()`: the app uses none of them, so no script can ask for them (`frontend/nginx/default.conf.template`).
- Dependencies: patch updates of dotenv 18.0.5, nodemailer 10.0.14, pg 8.23.1, @tanstack/react-query 5.104.1, vite 8.3.2, vitest 5.0.3, supertest 7.3.1 and smtp-server 3.19.17. `npm audit` reported 4 high advisories, all inside the Prisma command-line tool (`mysql2`, which only MySQL uses, and `deepmerge-ts`, which merges the project's own `prisma.config.ts`), neither reachable from a request; root `overrides` pin the fixed `mysql2` 3.24.5 and `deepmerge-ts` 8.0.2 (no fixed Prisma 7 release exists) — `npm audit` now reports 0. (`npm ls` still prints "invalid" for these two: an npm display bug with overrides in workspaces; `npm ci` installs them correctly.)

## [0.1.0] - Architecture Baseline Reset (2026-09-27)

### Added
- Consolidated monorepo baseline (Express 5, Prisma 7, React 19, PostgreSQL 15).
- Unified `/api/v1` API, single-schema Prisma migration chain, and role-based access control.
- Pure eligibility evaluation engine, database-level audit chaining, and background jobs.
- The version at the foot of the sidebar and in the FHIR `CapabilityStatement`, both read from `package.json`.

### Changed
- Reset application versioning to 0.1.0 (SemVer development baseline). The packages were numbered `4.0.0` ("V04"); no code, schema or migration changed with the number.
- `.env.example` lists every setting the backend reads (added `TELEGRAM_UPDATES`, `TELEGRAM_WEBHOOK_SECRET`, `SCFHS_DRIVER`, `SCFHS_API_URL`, `SCFHS_API_KEY`, `BADGE_SIMULATOR`).

### Superseded
- V03 (`nurse_appV03`) and its database `nurseapp` are superseded by this system. They were never part of this repository, so nothing was removed from it; what V04 dropped from V03 while being rebuilt is recorded in [docs/CLEANUP_REPORT.md](docs/CLEANUP_REPORT.md).
